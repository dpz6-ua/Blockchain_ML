\section{Implementation and Experimental Setup}
\label{sec:implementacion}

To empirically isolate and quantitatively evaluate the temporal and computational overhead introduced by the traceability and auditability layer, we deployed an experimental testbed representative of a distributed vehicular computing environment.

\subsection{Hardware and Software Infrastructure}
The empirical evaluation was conducted using two physical workstations interconnected within the same local area network (LAN). Their technical specifications are detailed in Table~\ref{tab:testbed_hardware}:
\begin{itemize}
    \item \textbf{Station 1 (Server, Validators, and IPFS)}: Hosts the Flower aggregation coordinator, the IPFS daemon, and all validator nodes of the permissioned Hyperledger Besu network (4 validators in configurations E1 and E4; 7 validators in E5). Each validator runs as an independent containerized service via Docker Compose, interconnected through a virtual bridge network that emulates the peer-to-peer consensus mesh of a vehicular consortium and exposes the JSON-RPC interface of the primary validator node as a gateway for the other entities.
    \item \textbf{Station 2 (Edge Nodes / Clients)}: Hosts and executes the federated training clients (members 2 and 3), which communicate with the aggregation server and the blockchain network over the physical LAN connection.
\end{itemize}

The software stack comprises Hyperledger Besu operating under the QBFT / IBFT 2.0 consensus protocol with a block generation period fixed at 5 seconds (\texttt{blockperiodseconds: 5}), supporting private transaction processing via Tessera and orchestrated using Docker Compose; the IPFS Kubo daemon (\texttt{v0.32.1}); Python \texttt{3.12} with PyTorch~\cite{paszke2019pytorch} for neural model training and inference; Flower (\texttt{flwr})~\cite{beutel2020flower} for federated gRPC communication; and the \texttt{web3.py} library for JSON-RPC connectivity with the EVM. All smart contracts, network configurations, and orchestration scripts are publicly accessible at \url{https://github.com/dpz6-ua/Blockchain_ML}.

The two workstations communicate over a 5~GHz Wi-Fi 802.11ac wireless local area network, exhibiting an average round-trip time (\textit{RTT ping}) of $3.8 \pm 1.1$~ms and a sustained bandwidth of 100~Mbps. The serialized binary model artifact (\texttt{NetCliente}) has a size of exactly $1.95$~MB. To ensure agile off-chain storage operations during iterative training, parameter uploads to IPFS are executed via the HTTP API endpoint \texttt{/api/v0/add?pin=false}, generating the CID identifier and adding the block to the local repository in milliseconds without the synchronous latency of pinning. We note that while \texttt{pin=false} optimizes immediate per-round latency, it does not inherently guarantee indefinite artifact persistence against future IPFS garbage collection sweeps; industrial production deployments would require explicit pinning policies or synchronization with a persistent IPFS cluster.

\subsection{Neural Network Model and Vehicular Dataset}
To simulate a real-world driver assistance system in Connected and Autonomous Vehicles (CAVs)~\cite{chellapandi2024federated}, we adopted the road traffic event classification dataset provided by CloudLab-AIA~\cite{cloudlabaia_flblockchain}.

The classification task addresses road hazard detection across four distinct categories:
\begin{enumerate}
    \item Traffic accident (\texttt{accident}).
    \item Heavy congestion / dense traffic (\texttt{dense\_traffic}).
    \item Adverse weather conditions (\texttt{meteorology}).
    \item Smooth traffic flow (\texttt{sparse\_traffic}).
\end{enumerate}

The dataset comprises 3,415 images distributed across: adverse weather (1,027), smooth traffic (947), dense traffic (778), and accidents (663). Images are preprocessed by resizing to a resolution of $32 \times 32$ pixels across three RGB channels and normalized. To ensure statistical comparability and eliminate distributional bias, the dataset is evenly split across $K=2$ clients following an Independent and Identically Distributed (IID) partition.

The implemented model (\texttt{NetCliente}) is a Convolutional Neural Network (CNN) structured into two consecutive convolutional blocks (with $3 \times 3$ kernels, ReLU activation, and Max Pooling subsampling), followed by two dense fully connected layers that project the feature vector to 4 output logits. Model training optimizes Cross-Entropy Loss using the Adam optimizer with a learning rate $\eta = 10^{-3}$, a batch size of 16 for training and 32 for validation, 3 local training epochs per federated round, and a total horizon of 30 federated rounds.

We emphasize that the primary objective of this study is not to design an optimal convolutional architecture or maximize classification accuracy, but rather to establish a realistic federated learning testbed to quantify and analyze system-level performance metrics (temporal overhead, validator quorum impact, and gas consumption). Model-level hyperparameter tuning, overfitting mitigation, and deeper architectures are deliberately left as future work, with the neural network serving here as a representative, realistic workload. Consequently, the decoupled architecture is directly transferable to other distributed learning domains (e.g., smart healthcare, smart grids, or collaborative finance), where blockchain audit logic remains identical and only IPFS off-chain transfer and hash computation scale with serialized model volume.

This experimental design enables controlled single-variable comparisons:
\begin{itemize}
    \item \textbf{Direct Blockchain overhead}: Comparing E1 vs. E2 in a single-machine setup, and E4 vs. E3 in a distributed network setup.
    \item \textbf{Effect of physical distribution}: Comparing E2 vs. E3 (without Blockchain) and E1 vs. E4 (with a 4-validator Blockchain).
    \item \textbf{Impact of validator committee size}: Comparing E4 (4 validators) vs. E5 (7 validators), evaluating latency impact when expanding the Byzantine consensus committee from $f=1$ to $f=2$.
\end{itemize}
